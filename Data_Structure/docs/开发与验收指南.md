# 开发与验收指南

本指南说明如何编译、运行、测试和验收数据结构 C 代码。学习过程中的早期单文件尝试可以保留；形成稳定模块时再拆分接口、实现、示例和测试。

## 环境要求

- 支持 C17 的 GCC。
- Windows PowerShell。
- 所有正式验收启用 `-Wall -Wextra -Wpedantic`，并要求零警告。

在仓库根目录运行辅助脚本：

```powershell
powershell -ExecutionPolicy Bypass -File .\Data_Structure\tools\run_c.ps1 -Source .\path\to\source.c
```

脚本会把程序生成到 `Data_Structure/.build/` 并立即运行。脚本会显示编译警告，但当前不会自动把警告转成失败；验收时必须人工确认没有警告。

也可以直接编译：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic source.c -o program.exe
```

## 从练习到模块

早期练习允许单文件保存学习轨迹。对应知识已经掌握后，稳定实现采用：

```text
module_name/
├─ module_name.h       类型、公开接口和接口约定
├─ module_name.c       实现
├─ demo.c              最小使用示例
└─ test_module_name.c  功能、边界与失败测试
```

头文件中的公开接口应说明：

- 参数允许的范围以及 `NULL` 是否有效。
- 成功和失败时的返回值。
- 操作失败时原结构是否保持不变。
- 动态内存由谁创建、谁拥有、谁释放。
- 关键时间复杂度；空间复杂度不直观时一并说明。

## 单个知识点的验收顺序

1. 闭卷说明定义、关系或关键不变量。
2. 在纸上追踪正常情况和一个边界情况。
3. 从空白完成指定范围的 C17 实现，不直接复制成熟版本。
4. 严格编译并消除所有错误和警告。
5. 运行适用的正常、边界和非法测试。
6. 检查每次成功分配的动态内存都有明确释放路径。
7. 说明时间和空间复杂度。
8. 保存代码、运行结果或答题记录作为证据，再更新进度与复测日期。

## 测试最低要求

测试必须根据接口语义选择，通常包括：

- 正常多元素操作。
- 空结构和单元素结构。
- 首位置、尾位置及容量边界。
- 非法位置、无效长度或允许测试的 `NULL` 参数。
- 重复值或目标不存在。
- 分配失败后的返回路径，以及正常路径上的完整释放。

对某个接口不适用的测试可以省略，但应能解释原因。测试通过后程序返回 0；断言失败、崩溃、越界、未初始化读取、重复释放和泄漏都不算通过。

## 错误分类

诊断时按以下顺序定位，避免把所有问题统称为“代码错了”：

1. 编译错误：语法、声明、类型或链接问题。
2. 运行错误：崩溃、越界、非法访问或资源错误。
3. 逻辑错误：算法步骤、指针关系或不变量错误。
4. 边界错误：空、满、首尾、单元素和非法输入处理不一致。
5. 风格问题：命名、格式、职责混乱；不覆盖前四类错误。

## 完成定义

“能够编译”不是完成。“初次学习通过”要求概念、手算或追踪、独立实现、测试与复杂度全部达到本次范围；“已掌握”还必须通过项目统一的 1、7、21 天主动复测。
